# AI Document Analysis Assistant

A lightweight prototype to analyse collections of client documentation using retrieval-augmented generation (RAG).

The application ingests a collection of publicly available UK government documents and provides:

* Semantic document retrieval
* Grounded question answering
* Structured extraction of risks, opportunities, actions, deadlines and stakeholders
* Executive summaries of up to 300 words
* Agent-based routing between analysis capabilities
* Retrieved source evidence and access to the original source documents

### Main components

**Document ingestion**

* Supports PDF and HTML content.
* Detects the actual file format rather than relying solely on the file extension.
* Removes unnecessary HTML elements and extracts the main document content.

**Chunking**

Documents are split into chunks of approximately 1,000 characters with 200 characters of overlap.

This provides a simple balance between retaining sufficient context and keeping retrieved passages small enough for the local language model.

**Semantic retrieval**

The prototype uses `all-MiniLM-L6-v2` from Sentence Transformers to create embeddings for document chunks.

The system retrieves the most semantically similar chunks for a given query.

A local cache stores the generated embeddings and chunks, avoiding the need to rebuild the retrieval index every time the application starts.

**Language model**

The prototype uses:

`mlx-community/Qwen2.5-3B-Instruct-4bit`

via MLX-LM.

A small local model was selected because the assessment was completed on an Apple Silicon laptop without relying on a hosted API.

The language model is loaded once and reused by the Streamlit application.

**Agent routing**

The agent selects the most appropriate capability for each request.

High-confidence requests are handled using deterministic rules. For example:

* Requests containing terms such as "risk", "opportunity", "action", "deadline" or "stakeholder" are routed to insight extraction.
* Requests containing "summary" or "executive summary" are routed to summarisation.
* Other requests are passed to the language model as a routing fallback.

This hybrid approach was chosen because testing showed that relying entirely on the small local language model for routing was less reliable.

## Capabilities

### Question & Answer

Users can ask factual questions about the document collection.

The system:

1. Embeds the question.
2. Retrieves the most relevant document chunks.
3. Provides those chunks to the language model as context.
4. Generates an answer constrained to the supplied context.
5. Displays the retrieved source evidence.

### Insight extraction

The system can identify:

* Risks
* Opportunities
* Actions
* Deadlines
* Stakeholders

The language model is instructed to return a structured JSON object, which the Python application then renders in the interface.

Source metadata is attached programmatically rather than being generated by the language model.

### Executive summary

The system retrieves the most relevant chunks and asks the language model to produce an executive summary of no more than 300 words.

Python applies an additional 300-word limit to the final output.

For this prototype, summarisation operates over the most relevant retrieved chunks rather than performing a comprehensive summary of every document.

---

## Dataset

The supplied dataset contains 11 documents covering topics including:

* Foundation models
* AI opportunities
* AI safety
* AI security
* Generative AI policy
* AI guidance for the UK public sector

The resulting retrieval index contains approximately 690 chunks.

One supplied file, `AI_Playbook_for_UK_Government.pdf`, contains HTML content despite its `.pdf` extension.

The ingestion pipeline therefore checks the actual file header and processes the document according to its underlying format.

## Running the application

### Prerequisites

* Python 3.11
* macOS on Apple Silicon for the MLX configuration used in this prototype
* Approximately 2 GB+ of local storage for the language model
* The supplied dataset in `data/dataset/`

### Setup

Create and activate a virtual environment:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Install the required dependencies:

```bash
pip install -r requirements.txt
```

### Run the Streamlit application

```bash
streamlit run app.py
```

The application will open in a browser.

## Caching and performance

The retrieval index is cached locally using a dataset/configuration fingerprint.

The application also uses Streamlit resource caching so that the retrieval model and language model remain loaded between interactions.

This avoids repeatedly:

* Recreating document embeddings
* Loading the language model
* Reinitialising the retrieval system

The prototype therefore performs best as a long-running Streamlit application rather than as a new Python process for every request.

## Engineering decisions

### Why RAG?

The use case requires answers grounded in a specific collection of client documents.

Retrieval-augmented generation allows the system to provide relevant document content to the language model rather than relying solely on the model's pretrained knowledge.

It also provides an evidence trail that users can inspect.

### Why semantic retrieval?

Keyword matching can miss conceptually related passages that do not contain exactly the same terminology as the user's question.

Semantic embeddings provide a lightweight way to retrieve conceptually relevant content without introducing a full vector database for this prototype.

### Why not a vector database?

The dataset is small, with approximately 690 chunks.

For a four-hour prototype, an in-memory NumPy-based index with local caching provides sufficient functionality without the operational overhead of introducing a vector database.

A production system with larger or frequently changing datasets could use a managed or persistent vector store.

### Why a local language model?

The assessment environment did not provide an OpenAI API key or equivalent hosted model access.

Running Qwen locally provided a self-contained prototype and avoided exposing the supplied documents to an external API.

### Why hybrid agent routing?

Initial testing showed that the small local model was not consistently reliable when used for all routing decisions.

Deterministic rules provide predictable behaviour for high-confidence intents, while the language model remains available as a fallback for ambiguous requests.

### Why not use an agent framework?

The workflow is relatively simple and only requires a small number of capabilities.

Direct Python routing was therefore sufficient for the prototype and reduced unnecessary abstraction.

A framework such as LangGraph or Semantic Kernel could become more useful if the system evolved to include more tools, state, multi-step workflows or complex agent interactions.

## Transparency and traceability

The application exposes:

1. The selected capability
2. The generated response
3. The retrieved source evidence
4. The original source document

This is intended to allow users to inspect the evidence behind an AI-generated response rather than treating the model output as authoritative.

The system is therefore designed to assist analysis rather than replace user judgement.

---

## Assumptions

* The supplied documents are the authoritative source material for the prototype.
* Users are expected to verify important outputs against the original documents.
* The prototype operates on a relatively small, static document collection.
* The local language model is sufficient to demonstrate the workflow but is not assumed to provide production-level reasoning quality.

---

## Limitations

### Retrieval

The prototype uses semantic similarity retrieval without a dedicated reranking stage.

Retrieval quality could therefore be improved with techniques such as hybrid lexical/semantic retrieval or a reranker.

### Source attribution

Source attribution is currently provided at document/chunk level.

The system does not perform formal claim-level citation verification.

### Summarisation

The executive summary operates over the most relevant retrieved chunks rather than the complete corpus.

A production implementation could use hierarchical or map-reduce summarisation to cover larger document collections.

### Language model

The local 3B parameter model is relatively small and can occasionally produce incorrect or overly broad interpretations.

Structured outputs are therefore not assumed to be automatically correct.

### Evaluation

The prototype contains functional testing but does not yet include a comprehensive evaluation dataset measuring retrieval recall, answer correctness, faithfulness or summary quality.

### Deployment

The application is a local Streamlit prototype rather than a production service.

A production deployment would require appropriate authentication, access control, monitoring, logging, secret management, scalable storage and model infrastructure.

---

## Potential production improvements

If this prototype were developed further, priorities could include:

1. A stronger hosted or enterprise-approved language model.
2. Persistent vector storage and metadata filtering.
3. Hybrid retrieval and reranking.
4. Automated evaluation of retrieval and generated answers.
5. More granular source/claim attribution.
6. Human review workflows for high-impact outputs.
7. Authentication and document-level access controls.
8. Monitoring for retrieval failures, hallucinations and model performance.
9. A production document ingestion pipeline for changing document collections.
10. Appropriate data protection and security controls for confidential client information.

---

## Summary

This prototype demonstrates a pragmatic approach to AI-assisted document analysis using:

* Multi-format document ingestion
* Semantic retrieval
* Retrieval-augmented generation
* Structured insight extraction
* Executive summarisation
* Agent-based capability selection
* Source evidence and document traceability

The implementation deliberately favours simplicity and explainability for the assessment context, while identifying the areas that would need further engineering before production use.
